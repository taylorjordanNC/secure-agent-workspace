Clone the deployment branch and remain in its repository root:

[source,bash,role="execute",subs="attributes+"]
----
mkdir -p "$HOME/git"
if test -d "$HOME/git/{saw_repo_dir}/.git"; then
  cd "$HOME/git/{saw_repo_dir}"
  SAW_REMOTE=$(
    for remote in $(git remote); do
      if test "$(git remote get-url "$remote")" = "{saw_repo_url}"; then
        printf '%s\n' "$remote"
        break
      fi
    done
  )
  if test -z "$SAW_REMOTE"; then
    SAW_REMOTE=workshop-fork
    test -z "$(git remote get-url "$SAW_REMOTE" 2>/dev/null)" || {
      echo "Remote $SAW_REMOTE already exists with a different URL" >&2
      exit 1
    }
    git remote add "$SAW_REMOTE" {saw_repo_url}
  fi
  git fetch "$SAW_REMOTE" {saw_repo_branch}
  git switch {saw_repo_branch} 2>/dev/null || \
    git switch --track -c {saw_repo_branch} "$SAW_REMOTE"/{saw_repo_branch}
  git pull --ff-only "$SAW_REMOTE" {saw_repo_branch}
else
  git clone --branch {saw_repo_branch} \
    {saw_repo_url} "$HOME/git/{saw_repo_dir}"
  cd "$HOME/git/{saw_repo_dir}"
fi
git branch --show-current
test "$(git branch --show-current)" = "{saw_repo_branch}"
git rev-parse HEAD
----

Generate your own SSH key pair on this workstation — shared keys are not
acceptable in any path — and, when absent, `$HOME/values-secret.yaml`:

[source,bash,role="execute"]
----
make generate-keys
chmod 600 "$HOME/values-secret.yaml"
----

Edit `$HOME/values-secret.yaml`. The active data-science BOM expects the NVIDIA
provider type, represented by the secret provider identifier `build`:

[source,yaml]
----
- name: inference
  fields:
  - name: provider
    value: build
  - name: model
    value: nvidia/nemotron-3-super-120b-a12b
  - name: api_key
    path: ~/.ngc-api-key
----

Use exactly one of `value` or `path` for `api_key`. Ensure a referenced key file
is readable by the user running the seed step.

Web search ships enabled: the data-science BOM profile creates a `brave`
provider in the default workspace that reads the `web-search` secret's
`api_key`. Point that field at a readable Brave key file. Tavily remains a
documented alternative: set the secret's `provider` to `tavily` with a Tavily
key instead.

The secrets land in the cluster's Vault at install time. With the Validated
Patterns framework, `make install` loads them (the Ansible `load-secrets`
role in the pattern's utility container). With the GitOps path of install —
the `saw-gitops` app-of-apps — there is no utility container, so seed the
Vault directly from the same values file. Run the seed after that cluster's
`saw-gitops` tree has converged: the script reads the `vault-init` Secret
the vault-config Job creates, and tells you if the tree is not there yet.

[source,bash,role="execute",subs="attributes+"]
----
./scripts/seed-vault.sh
----

The script reads the same `$HOME/values-secret.yaml`, fetches the Vault root
token from the `vault-init` Secret (the vault-config Job creates it), and
seeds the shared prefix `secret/hub` via `oc exec` — no local vault CLI and
no port-forward. Re-run it whenever the values change; the ExternalSecrets
pick the update up on their next refresh.

The private SSH key remains on the control node and is also seeded into the
cluster's Vault so the setup Job can configure the VM; only the public key is
injected into the VM. In a multi-user workshop each workstation seeds its own
key under a per-user prefix
(`VAULT_PREFIX=secret/hub/saw-<name> ./scripts/seed-vault.sh`), and the
saw-users chart points that user's secrets at the same prefix. Never commit
the values file, provider credentials, or generated private key.

The deployment override assigns the sample owner `alice`. The current
quickstart seeds the isolated lab account `alice` with password `alice`; use it
only for this workshop and change or remove it afterward. For any shared or
non-lab environment, replace the seeded account and update
`overrides/openshell-saw.yaml` before installation.
